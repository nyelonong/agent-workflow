# omp adapter

Use the `ask` tool for required decisions: give concrete options, mark the recommended index, and stop until the user answers. It is interactive-only and a cancelled `ask` is a refusal, not a decision. Never treat an edit, command, or sandbox permission prompt as product or implementation approval.

Load the personal `workflow` skill with `read` at `skill://workflow` when the user asks for the workflow, or let them invoke `/skill:workflow`; load `skill://task-review` before committing production changes. Inspect with `read`, `bash`, `grep`, and `glob`. For approved multi-task planning, dispatch the `task` tool at most once with an `architect` agent, when one is defined in `~/.omp/agent/agents/`, and only when an independent view materially improves the plan; its output is advisory. Dispatch `reviewer` only when the global independent-review boundary applies, the user requests it, or credible uncertainty justifies optional review, and use `scout` for read-only codebase research. Ordinary parent work dispatches no subagent except the required bounded task-review gate runner. Always delegate plan/diff gate preparation and invocation under the shared task-review skill, using native child model controls to always use GPT-6 Luna (`gpt-6-luna`) within the current provider and runtime scope; if unavailable or disallowed, stop rather than substituting another model. Keep the parent model unchanged; unavailable delegation/model selection/waiting blocks rather than falling back to the parent. The parent retains verification, corrections, consumption and commits.

omp-specific settings, hooks, extensions, MCP servers, and repository `.omp/` or standalone `AGENTS.md` files remain authoritative within their narrower scope.
